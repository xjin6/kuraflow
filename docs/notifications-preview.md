# 管理端待办与通知

2026-10-20 已应用 `0009_notifications.sql` 并发布到正式环境，版本和回执见 `docs/cloud-deployment-status.md`。

2026-10-21 本地预览已将待办移到「经营概览」下方的独立菜单，分「系统推送」「手动记录」两个 tab；此位置调整尚未发布。

系统待办根据当前业务状态派生：未解决的整单异常和单品缺货、逾期订单、今日待配货／待出发，以及低库存。每笔订单仅显示一个优先事项，异常优先于逾期和普通配货。正常配送不单独占待办。点待办进入货单或库存操作，不通过通用完成按钮绕过业务校验。

配货备注新增“缺货／普通备注”类型。缺货可明确解决或随配齐自动解决，备注保留；撤销配齐只重新打开由配齐自动解决的缺货。手动解决不改变数量，也不解除原来的配货完成校验。旧备注中明确写出的缺货在未配齐时也会显示，普通备注不进入异常待办。整单异常保留 `issueResolvedAt` 状态，门店显示已处理结果但不接收内部单品配货备注。

铃铛显示管理员自己的未读数。通知按实际变化生成：新订单、主要配送阶段、缺货／异常、新催单和进入低库存。持续低库存不重复提醒；库存恢复后再次跌入阈值才生成新事件。首次加载不编造历史通知，旧业务仍显示在待办。阅读和全部已读仅更新当前账号的已读记录，不能修改订单、库存、备注或其他管理员的阅读状态。

通知 API 仅管理端可用，按当前租户和个人账号隔离。事件与业务变更在同一个 D1 事务中写入，幂等重试不会重复生成。分页每页 50 条；全部已读使用客户端看到的通知边界，不吞掉之后到达的新消息。通知历史不因对应待办已解决而删除，展示当前业务状态。

本地 4173 演示使用独立通知日志，保留原 localStorage 业务数据；8787 账号预览使用相同服务端 API 和 D1。两者数据来源仍分开。静态演示手机入口为 `/__local-preview/phone?page=overview`，420×912 CSS 视口。

代码入口：

- `notification-domain.js`：事件差异、缺货判断、通知当前状态。
- `local-notifications.js`：静态演示日志和个人已读。
- `notifications-ui.js` / `notifications.css`：通知中心、筛选、阅读和导航。
- `overview-data.js` / `tasks-ui.js`：派生待办与独立页面业务入口；`overview-ui.js` 保留经营统计。
- `backend/notifications.js`：按租户和个人作用域分页及标记已读。
- `backend/repository.js`：业务操作和通知的原子事务。

验证涵盖事务回滚、重试竞争、租户隔离、个人已读、全部已读边界、缺货解决／撤销、低库存阈值、普通备注排除、分页、错误恢复、XSS、键盘焦点及手机布局。浏览器已核对：缺货产生待办和通知，已读不完成待办，配齐移出异常，撤销恢复待办。演示验收后恢复原配货数量和备注。
