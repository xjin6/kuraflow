# 平台与员工账号：本地可操作版

本轮未部署、未迁移正式数据库。原始 HTML 预览与浏览器保存数据仍在 http://127.0.0.1:4173/ 。新的账号版使用独立的本地 Workers/D1 运行环境，位于 http://localhost:8787/ 。

## 入口与启动

- `npm run dev:accounts`：构建当前云端前端和 Worker，启动有持久化的本地账号版。
- 首次进入 http://localhost:8787/local-setup ，由使用者自己设置平台负责人的密码。初始登录号由系统随机生成；激活完成后在员工登录或平台管理登录使用登录号与密码。
- 后续 http://localhost:8787/?login=platform ：平台管理；http://localhost:8787/?login=staff ：厨房及门店员工登录。
- 本地数据在 `private-preview/accounts-runtime/`，开发用加密密钥及平台初始邀请在 `private-preview/`。均被忽略且不进入公开构建。重启保留数据；尚未激活的平台邀请会在重启时重新生成。
- 平台初始列表保留一份从源材料创建的独立厨房样例，可以点“开通负责人”启用新账号方式。没有读取、覆盖或同步 4173 浏览器中手工增加的数据。

## 已实现

平台管理客户：开通中央厨房及负责人、生成 4×4 组织识别码、套餐文字配置、有效期、厨房及每家门店的独立名额（默认各 3 个，包含负责人）、停用与恢复客户、负责人密码恢复。

厨房／门店“员工账号”：按组织查看员工、姓名和联系方式、10 位全局唯一登录号、首次开户复制邀请、24 小时一次性激活链接、本人设置 12～128 字符密码、修改自己的密码、重发邀请、上级重置密码、停用／重新启用普通管理员、操作记录。

负责人保护：一个组织恰有一个负责人；不能停用负责人。厨房负责人由平台恢复，门店负责人可由厨房负责人或平台恢复。普通管理员不能管理账号，厨房负责人只能管理自己厨房和其门店，门店负责人只能管理本店。

## 权限与存储

- 数据库迁移：`backend/migrations/0005_staff_accounts.sql`。个人账号、口令哈希、邀请码、会话单独保存，不进入 `/api/state`。
- 密码：随机盐 scrypt（N=32768, r=8, p=3），常量时间校验；邀请码和会话只保存 SHA-256 摘要。无邮件、短信依赖。
- Cookie：正式环境 `__Host-kuraflow_account`，Secure、HttpOnly、SameSite=Strict。仅 `LOCAL_TEST=1` 的 loopback 开发地址使用本地 HttpOnly Cookie。
- 激活只可用一次；密码重置使旧密码、旧邀请和既有会话立即失效。停用、厨房到期或删除门店也会拒绝后续访问。
- 名额包含启用和待激活账号；创建／重新启用在 SQL 条件更新与事务内限制人数。停用不删除历史记录，并释放普通管理员名额。
- 登录同时受 IP 限流和登录号限流。账号密码、激活链接与 Cookie 不写入业务日志。
- 平台账号不能直接读取客户 `/api/state`、商品价格、订单或私有材料。平台的支持权限目前限于客户配置和账号恢复，没有实现冒充客户操作。
- 员工业务操作沿用原来的租户／门店隔离，并记录人员 ID 与姓名。

## 兼容与发布前处理

原通行密钥／门店码入口暂时保留。开通中央厨房后，负责人激活新的个人账号时，该厨房旧管理员会话不再用于业务接口；门店在本店负责人激活后停止使用共享码登录。新组织识别码与旧登录凭据分别存放，识别码本身不能登录。

正式发布需要先备份并应用新迁移，再通过受控的运维流程创建平台负责人激活链接、部署 Worker 与资产；不得把本地开发 `/local-setup` 入口放入线上，也不得将本地演示数据导入正式数据库。实际生产迁移和平台账户开通尚未执行。

现有限制：套餐是权限配置，不包括收费扣款；尚未做负责人转交、多组织账号切换、邮件自助找回或平台其他员工管理。跨浏览器开户时，应使用本人常用的浏览器完成激活。

## 验证结果

7 项新增账号集成检查覆盖真实 D1 事务、并发名额、一次性激活、重置与停用、组织隔离、平台配置和原有业务接口衔接。其余后端检查通过；原有登录码升级测试中使用标准 Base64 的随机失败已改为与实际存储一致的 Base64URL。另在隔离的真实 Workers 运行环境中验证 scrypt 激活、密码登录和 Secure Cookie。前端构建、脚本语法与新样式解析通过；本地两套服务正常响应。当前会话没有可调用的浏览器检查工具，未完成页面目视验收。
