# 三端登录与管理员账号（已上线）

## 最终规则

- 平台入口：`/?login=platform`。只需粘贴复杂平台密钥，不使用用户名或人员密码。
- 厨房入口：`/?login=kitchen`。负责人使用 16 位字母数字码（4×4），管理员使用账号名与密码。
- 门店入口：`/?login=store`。同样分为负责人登录／管理员登录两个页签。
- 厨房与门店页面不展示平台入口；平台仅通过独立地址进入。负责人／管理员页签切换和登录报错后也遵循这一规则。
- 每家厨房、每家门店都有 1 个负责人，另外最多 3 个管理员；负责人不占名额。
- 负责人直接设置管理员账号名、初始密码、姓名与联系方式。管理员可在“员工管理 → 我的账号”修改自己的账号名／密码，保存后重新登录。
- 账号名 3～32 位，支持文字、字母、数字和 . _ -，规范化后全平台唯一。密码 12～128 个字符。

## 入口与界面

平台左侧有中央厨房、员工管理、操作记录。客户行提供负责人码、员工管理、设置。员工管理可选择厨房，再切换到该厨房的门店。厨房和门店工作台均有员工管理入口。

开户表单改为 JSON POST，使用 `getAttribute('id')` 判断表单而非会被同名控件覆盖的 `form.id`；隐藏字段改名 tenantId/accountId。提交期间阻止重复提交，重试沿用 requestId。失败保留输入，不再将姓名、联系方式或密码拼进网址。

## 存储与权限

- 新表：0005_staff_accounts.sql、0006_master_keys.sql；不覆盖业务表。
- 平台密钥：48 随机字节（384 bit），本地私有文件交付，数据库只存 SHA-256 摘要。
- 负责人码：安全随机数＋拒绝采样，保证 16 位且包含字母与数字。SHA-256 索引用于登录；AES-GCM 密文用于授权的上级查看／复制，AAD 绑定账号、厨房和门店，沿用 STORE_CODE_KEY。
- 普通管理员不能读取、复制或重置负责人码，业务状态接口不返回码或密码哈希。平台不能直接进入客户业务数据接口。
- 密码使用独立盐的 scrypt，常量时间验证。所有写请求检查 Origin；登录受 IP 限流，管理员登录另有账号限流。
- 负责人码重置使旧码和该负责人的会话失效，普通管理员会话不受影响。修改管理员凭据／停用账号会撤销该管理员的会话。
- 开通厨房及创建管理员带幂等 requestId；创建门店沿用业务命令幂等键。3 人名额在 D1 事务内检查，包含尚未停用的旧版待设置密码账号，避免并发超额。

## 迁移与发布

现有公司及门店保留原 ID 和业务数据。为厨房补建负责人，为门店补建负责人身份；已有可解密的有效 16 位门店登录码保留。旧密码版负责人转为码登录，旧负责人密码、会话及邀请失效。原通行密钥／旧共享码 API 入口退役为 HTTP 410，新入口统一处理码登录。

平台生产密钥位于 `private-deploy/platform-key.txt`，本地密钥位于 `private-preview/platform-key.txt`，两者独立且不进入公开构建。发布准备程序只把密钥摘要放入数据库迁移包。重跑不会自动轮换已有平台密钥。

发布过程：验证 Cloudflare 目标与绑定，记录 D1 Time Travel 恢复点，应用新增表及平台引导事务，发布 Worker／资产，使用平台 API 执行幂等的业务身份迁移，再核对线上资源、登录与权限。保留原 DB、MEDIA、STORE_CODE_KEY；不重新导入本地样例数据。
